# WhatsApp booking welcome branding

Set `WA_CLINIC_BRANDING_JSON` on the API and worker to an array of `{tenantId, facilityId, welcomeImageUrl}`. Each entry must match an existing public booking site and its allowed origin. Only public HTTPS PNG/JPEG URLs without credentials, query strings or fragments are accepted. Duplicate clinic entries fail startup. The published image is sent with the existing welcome/consent message; prompts longer than Meta’s 1,024-character image-caption limit remain intact text. Uploaded files and document attachments still use the existing upload controls and guards.

Meta delivery can be configured with `WA_APP_ID`, `WA_APP_SECRET`, `WA_GRAPH_VERSION`, `WA_VERIFY_TOKEN`, `INTEGRATIONS_ENCRYPTION_KEY`, `INTEGRATIONS_PUBLIC_ORIGIN` and `WA_MANAGED_SENDING_ENABLED=true`. `META_SIGNUP_CONFIG_ID` is additionally required for embedded signup; do not invent a signup configuration ID for an operator-connected test number. All credentials stay on the server. The existing encrypted managed connection, provider-verified phone binding, signed webhook, consent, booking authority and delivery checks still apply.

For a Meta test connection, store `testMode: true` and an explicit E.164 `testRecipients` array in server-owned managed-connection metadata. The booking engine ignores unapproved recipients and outbound dispatch rechecks the current allowlist under the connection lock. Missing/empty allowlists fail closed. Test booking responses begin `TEST CHAT — `. Test confirmations create appointments in that tenant’s database, so use a designated test tenant and synthetic names. A test setup must not be represented as hospital production activation. Meta test tokens expire; delivery acceptance is distinct from delivered/read receipts and patient-initiated reply verification.

The image is a URL-backed welcome asset; it is not a WhatsApp profile-image update or a Meta-approved outbound message template. Production activation still needs verified clinic details and an appropriate permanent number/token. Preserve any existing app/WABA subscriptions and use the connected phone’s callback override for tenant routing.

## Native booking choices and patient-details form

Set server-owned connection metadata `bookingUI: "interactive"` with a provider-validated `detailsFlowId` and `detailsFlowMode` (`draft` for Meta’s test preview, otherwise `published`). The source form for Swastikaa is `docs/whatsapp/swastikaa-booking-details.flow.json`. Upload it to the same WABA as the bound phone and confirm validation/status with Meta before activation. Publishing can be blocked by Meta’s account-integrity checks even when JSON validation passes; draft preview acceptance does not establish production eligibility.

Native mode uses welcome/consent buttons, reminder buttons, paginated specialty/doctor/time lists, date choices, a patient-name Flow, and confirmation buttons. Callback selections retain their IDs separately from display titles. A fresh menu token scopes every choice to the current conversation step; form tokens are scoped to the pending patient-details step. Appointment authority verifies the current confirmation button, stored patient name and signed slot token before committing. Typed YES/CONFIRM and stale selections cannot authorize native-mode bookings. Other clinics retain their existing mode. Apply the `20261027110000_whatsapp_interactive_booking.sql` migration before starting this runtime.

## Sri Lakshmi-compatible sandbox mode

For the original Sri Lakshmi interaction pattern, set server-owned connection metadata `bookingUI: "interactive"` and `detailsMode: "chat"`. All choices, consent and confirmations use native buttons/lists; only the patient name is entered as a normal message. This mode does not create, publish or send a Meta Flow and does not depend on Flow eligibility. A native Flow can remain configured for future use without being invoked. Production booking authority still checks the current confirmation button and signed slot. The dedicated Meta developer test number and approved-recipient list remain required for phone testing.
